一、系统概述与术语

在现有实名制打卡基础上，新增双人合拍验证机制。核心逻辑：打卡人完成常规打卡后，系统按规则随机要求打卡人与工地上另一人完成双人实时合影验证。监管端提供数据看板、规则配置、抽验记录、抽验汇总、数据统计五大模块。

术语定义

术语英文/字段名定义
打卡人checkin_user被系统随机抽中需完成双人合拍的实名制人员，用自己的手机进行合拍拍照
合拍人partner_user从候选人池随机抽取，需配合打卡人完成双人合拍的人员。合拍人只需到场，拍照由打卡人手机完成
抽验co-photo-verification"双人合拍验证"的简称，在常规打卡基础上增加的随机验证环节
候选人池candidate_pool可供抽取作为合拍人的在册人员集合，分上班卡/下班卡不同范围
确认窗口confirm_window合拍人响应时限，运维配置项（默认5分钟），在规则配置模块按组织域调整
执行窗口execution_window从被抽中到完成合拍的总时限，运维配置项（默认15分钟），在规则配置模块按组织域调整
降级打卡downgrade候选人池枯竭或执行窗口超时后，降级为单人打卡并标记异常
项目规则例外rule_exception特定项目的独立规则配置，标记 is_locked=true，不被上级组织域下发覆盖。权限下放至地市、区县级单位自行管理
合拍人产生方式partner_selection_mode运维配置项：system_random（系统随机）/ self_select（自选）。自选模式下被抽中人员从可选列表自行选择合拍人
拍照设备分配photo_device_mode运维配置项：随机判定由谁手机拍照。默认各50%，可配置偏向打卡人或合拍人
刷脸验证状态face_verified_today当日是否已完成微信刷脸验证。当日双人打卡流程未走完前，退出再进入免重复刷脸

三、小程序端 — 完整交互规范

3.1 微信刷脸验证页（mp-checkin-face.html）新增

被抽中需双人打卡的人员，点击打卡按钮后先进行微信刷脸验证，通过后方可进入双人打卡流程。

  • 触发条件：系统判定被抽中需双人合拍时，打卡按钮点击后跳转此页
  • 三态切换：初始（人脸图标+"开始刷脸验证"按钮）→ 加载中（spinner动画2秒）→ 成功（绿色对勾，自动跳转合拍触发页/选择页）/ 失败（红色叉号+"返回打卡页"按钮）
  • 当日免重复：当日双人打卡流程未走完前，退出小程序再进入时点击打卡按钮跳过刷脸直接进入双人打卡验证页。通过 face_verified_today 字段判定
  • 刷脸失败：返回打卡页，不能完成打卡（按系统原流程处理）
  • 技术实现：调用微信原生人脸核验接口 wx.startFacialRecognitionVerify

3.2 合拍人选择页（mp-co-photo-select.html）新增

当规则配置为自选模式时，刷脸通过后进入此页，由被抽中人员自行选择合拍人。

  • 可选人员列表来源：当前工地在场的岗位人员，已打上班卡但未打下班卡的人员，排除自己。接口 GET /api/co-photo/candidates?projectId=X
  • 5分钟限时（运维可配）：页面顶部倒计时，超时未选择则系统按随机抽取原则抽取一名
  • 列表为空：降级为单人打卡，展示"当前无可选合拍人员，已降级为单人打卡"
  • 选择确认：点击人员→选中高亮→底部"确认选择"按钮→跳转合拍触发页
  • Demo面板：3种情景切换：正常选择 / 列表为空 / 选择超时

3.3 合拍触发通知页（mp-co-photo-trigger.html）

打卡人完成单人打卡后被系统抽中，进入此页。页面通过 URL hash 切换 5 种情景：

Hash情景触发条件模块②模块④模块⑤模块⑥
#normal正常等待抽中，等待确认—（不显示）显示待确认（旋转）占位15:00
#confirmed已确认合拍人接受—（不显示）不显示绿色勾+时间实际倒计时
#swapped被拒换人第1人拒绝，系统换第2人1人拒绝→换人提示显示待确认（旋转）占位15:00
#lastperson最后一人第2人拒绝，最后机会2人拒绝轨迹显示待确认（旋转）占位15:00
#exhausted候选人枯竭池中无可用候选人—（不显示）不显示不显示不显示
开发要点：5种情景通过 hash 路由切换，模块②④⑤⑥按上述规则显隐。合拍人姓名/头像/手机号为 demo 静态数据，实际开发需从接口获取。

拍照按钮逻辑：合拍人确认前，「开始拍照」按钮灰显不可点击，下方提示"待合拍人确认后方可开始拍照"。合拍人确认后（情景二）按钮恢复可点击，跳转合拍相机页。情景五（池枯竭）不受此限制，直接跳转单人打卡拍照页。

拍照设备随机分配 新增：合拍人确认后系统立即随机判定由谁手机拍照（概率运维可配）。若抽中合拍人手机拍照，打卡人端点击拍照按钮时弹窗提示"系统抽中需使用合拍人 XX 手机进行合拍验证"，关闭弹窗后按钮禁用显示"等待合拍人拍照中"。合拍人端在确认结果页（mp-co-photo-accept.html）展示"📷 开始合拍"按钮，跳转拍照页。

确认状态刷新机制：等待合拍人确认的状态卡片中，标题右侧提供蓝色「刷新」按钮，用户可手动点击立即查询合拍人是否已确认/拒绝。若用户未手动点击刷新，前端每 45秒 自动轮询一次合拍人确认状态。刷新期间按钮显示"刷新中…"并暂时禁用，防止重复请求。

3.4 合拍邀请处理页（mp-partner-invitation.html）

  • 5分钟确认倒计时：页面顶部实时倒计时，超时自动触发拒绝逻辑
  • 接受流程：点击"接受，前往汇合" → 跳转 mp-co-photo-accept.html（汇合指引页，非拍照页）
  • 拒绝流程：点击"拒绝（需填写原因）" → 弹出拒绝原因面板（5个预设选项+自定义输入） → 确定 → 跳转 mp-co-photo-refuse.html

3.6 核验结果页（mp-co-photo-success.html）

  • 三态切换：demo 面板按钮控制加载→通过→未通过三种状态
  • 加载态：2步流程（照片已拍摄 → 正在核验人脸信息），不暴露后端技术细节
  • 通过态："考勤打卡成功"，不展示核验分数/GPS/核验详情
  • 未通过态：原因说明 + 重新拍摄 + 降级单人打卡选项
  • 严禁暴露：所有文案中不出现"百度API""后端上传""第三方接口"等字眼

3.7 小程序"我的"页面（mp-my.html）

  • 角色切换：手机框外有 demo 切换按钮，实际开发通过登录态自动判定
  • 人员信息：无"打卡人"/"合拍人"角色标签
  • 合拍验证模块：全局可见（两个角色均有），合拍请求不在主页展示卡片
  • 红点提醒 新增："合拍验证"应用图标上，当合拍人有待处理合拍代办时显示红点标识（.menu-badge，9px红色圆点+白色边框）。打卡人角色隐藏红点，合拍人角色有待处理请求时显示

3.8 消息公告页（mp-message.html）

  • 无顶部页签区分，合拍请求混入通知列表
  • 合拍请求消息按钮为"去处理"，跳转 mp-partner-invitation.html

3.9 合拍验证记录（mp-co-photo-records.html）

  • Tab1 抽验记录：我作为打卡人的记录（验证通过/未通过）
  • Tab2 协助记录：我作为合拍人的记录（同意协助/拒绝请求）
  • 无"查看详情"按钮；每条记录字段统一固定

4.2 数据看板（index.html）

包含 5 大区块（从上到下）：

  1. 统计卡片（5个）：启用区县数 / 抽验触发人次 / 抽验通过率 / 拒绝人次 / 降级人次，每卡片右下角有对应子菜单链接

4.3 规则配置（rule-global.html）

双页签（同页面内切换，非跳页）：

  • 全局配置：表格列：组织域/级别/上班卡抽取率/下班卡抽取率/候选人池阈值/人员更换限制/抽验有效期/操作。配置弹窗含：组织域信息（只读）、抽取率、候选人池阈值、合拍人产生方式（系统随机/自选）、自选选择限时、拍照设备分配、下发组织域（树形下拉多选）
  • 项目规则例外：表格列：项目名称|施工许可/项目区划/上级默认规则对比/项目实际规则（橙色📋标记例外项）/操作。新增例外→模糊搜索选项目；修改例外→项目名只读。权限下放 新增：地市、区县级单位可自行添加/解除其辖区内的特殊规则项目，无需逐级上报
关键逻辑：项目规则例外标记 is_locked=true，全局规则下发时跳过这些记录（UPDATE 语句加 WHERE is_locked=false）。权限下放：下级单位添加的例外项目，上级单位可查看但不可修改；上级单位可强制解除下级的例外设置。

4.5 抽验记录详情（record-detail.html）

  • 三列信息卡片布局（人员/项目/验证结果），无右侧空白

4.6 抽验汇总（summary.html）

5.3 定时任务

任务频率逻辑
确认窗口超时扫描每 30 秒扫描 status=pending AND now() > confirm_deadline，自动标记 timeout 并触发换人判定：若当前已尝试的候选人次数超过配置上限 N，则降级为单人打卡；否则自动抽取下一个候选人
执行窗口超时扫描每 30 秒扫描 status=confirmed AND now() > expire_at AND result IS NULL，标记 downgrade
自选选择超时扫描 新增每 30 秒扫描 selection_mode=self_select AND partner_user_id IS NULL AND now() > select_deadline，系统随机抽取一名候选人
并发控制：抽取合拍人时使用 Redis 分布式锁 (lock:partner:{userId}, TTL=15min)，防止同一人被多个打卡人同时抽中。
防作弊审计：合拍人提交确认/拒绝时，后端必须记录合拍人的 GPS 坐标和客户端 IP 地址，写入 co_photo_request.partner_response 字段。用途：(1) 核查合拍人是否在项目工地附近——若挂职者远程操作，其 GIS 必然偏离工地坐标，直接成为挂职证据；(2) 频繁拒绝/超时的合拍人，结合 GIS 数据可判断是否"人不在现场"。

八、开发注意事项

严禁向用户暴露任何第三方服务商名称。所有UI文案中不得出现"百度API""百度人脸核验""后端上传""阿里云"等字样。统一使用"人脸核验""系统"等笼统表述。
  1. 打卡人不能拒绝/更换系统分配的合拍人，无对应UI和API
  2. 合拍拍照强制实时拍摄，调用 wx.chooseMedia({ sourceType: ['camera'] })
  3. 照片上传前客户端加水印（GPS+项目+人员+时间）
  4. 规则下发时排除 is_locked=true 的项目例外记录
  5. 所有时间字段存储为 UTC timestamp，前端展示时按用户时区转换
  6. 侧边栏 7 个菜单图标以 index.html 为基准（统一样式）
  7. 账号级别切换功能在原型中为 demo 下拉框，实际开发通过登录态 org_level 判定
  8. 项目搜索使用 LIKE 模糊匹配（WHERE project_name LIKE '%keyword%'），输入 ≥2 字触发
  9. 折线图/图表类组件建议使用 ECharts，原型的静态 SVG 仅供参考布局
  10. 刷脸验证 新增：调用微信原生人脸核验接口，当日 face_verified_today=true 时跳过刷脸直接进入双人打卡页
  11. 拍照设备分配 新增：合拍人确认后后端立即判定拍照设备，通过 WebSocket 推送结果到双方前端。合拍人手机拍照时打卡人端禁用拍照按钮
  12. 自选模式 新增：可选人员列表查询需排除自己 + 已锁定人员，超时自动随机抽取需在后端执行（防止前端篡改）
  13. 红点提醒 新增：合拍人有待处理请求时图标显示红点，通过查询 co_photo_request WHERE partner_user_id=X AND status=pending 判定
  14. 权限下放 新增：项目规则例外按 created_org_level 过滤，下级单位只能管理本辖区的例外项目
  15. 照片不展示 新增：抽验记录详情接口返回数据中不包含照片URL，仅返回核验结果和分数。照片存储在后端但前端不展示
  16. 数据统计 新增：取消风险评分定时任务，数据统计页面直接查询聚合数据，无风险评级逻辑
