一、系统概述与术语

在现有实名制打卡基础上，新增双人合拍验证机制。核心逻辑：打卡人完成常规打卡后，系统按规则随机要求打卡人与工地上另一人完成双人实时合影验证。监管端提供数据看板、规则配置、抽验记录、抽验汇总、风险预警五大模块。

术语定义

术语英文/字段名定义
打卡人checkin_user被系统随机抽中需完成双人合拍的实名制人员，用自己的手机进行合拍拍照
合拍人partner_user从候选人池随机抽取，需配合打卡人完成双人合拍的人员。合拍人只需到场，拍照由打卡人手机完成
抽验co-photo-verification"双人合拍验证"的简称，在常规打卡基础上增加的随机验证环节
候选人池candidate_pool可供抽取作为合拍人的在册人员集合，分上班卡/下班卡不同范围
确认窗口confirm_window合拍人响应时限 = 5分钟，写死不可配置
执行窗口execution_window从被抽中到完成合拍的总时限 = 15分钟，写死不可配置
降级打卡downgrade候选人池枯竭或执行窗口超时后，降级为单人打卡并标记异常
项目规则例外rule_exception特定项目的独立规则配置，标记 is_locked=true，不被上级组织域下发覆盖

角色体系

角色端主要操作
打卡人小程序单人打卡 → 被抽中 → 查看合拍通知 → 联系合拍人 → 双人合拍拍照 → 查看核验结果
合拍人小程序收到通知 → 查看邀请 → 接受/拒绝 → （接受后）前往汇合 → 配合拍照
省级监管监管端全省看板 → 配置省级默认规则 → 下发至地市 → 风险预警全局视图
市级监管监管端本市看板 → 微调规则 → 本市风险预警 → 下发督办
区县监管监管端本区看板 → 查看风险详情 → 标记处理

三、小程序端 — 完整交互规范

3.1 合拍触发通知页（mp-co-photo-trigger.html）

打卡人完成单人打卡后被系统抽中，进入此页。页面通过 URL hash 切换 6 种情景：

Hash情景触发条件模块②模块④模块⑤模块⑥
#normal正常等待抽中，等待确认—（不显示）显示待确认（旋转）占位15:00
#confirmed已确认合拍人接受—（不显示）不显示绿色勾+时间实际倒计时
#swapped被拒换人第1人拒绝，系统换第2人1人拒绝→换人提示显示待确认（旋转）占位15:00
#lastperson最后一人第2人拒绝，最后机会2人拒绝轨迹显示待确认（旋转）占位15:00
#exhausted候选人枯竭池中无可用候选人—（不显示）不显示不显示不显示
#offduty下班卡抽中下班卡被抽中—（不显示）显示待确认（旋转）占位15:00
开发要点：6种情景通过 hash 路由切换，模块②④⑤⑥按上述规则显隐。合拍人姓名/头像/手机号为 demo 静态数据，实际开发需从接口获取。

3.2 合拍邀请处理页（mp-partner-invitation.html）

  • 5分钟确认倒计时：页面顶部实时倒计时，超时自动触发拒绝逻辑
  • 接受流程：点击"接受，前往汇合" → 跳转 mp-co-photo-accept.html（汇合指引页，非拍照页）
  • 拒绝流程：点击"拒绝（需填写原因）" → 弹出拒绝原因面板（5个预设选项+自定义输入） → 确定 → 跳转 mp-co-photo-refuse.html

3.3 合拍拍照页（mp-co-photo-camera.html）

项规范
屏幕尺寸手机外框 390×680px（竖屏），取景区域 780×351px（横构图）
人脸引导框两个虚线头肩轮廓 SVG（白色描边），无文字标签
水印叠加GPS坐标 + 项目名称 + 打卡人姓名 + 时间戳，拍照时自动叠加在照片底部
快门按钮白色圆环 + 蓝色内圈，位于取景框右侧
禁止相册调用 wx.chooseMedia({ sourceType: ['camera'] })，不传 album

3.4 核验结果页（mp-co-photo-success.html）

  • 三态切换：demo 面板按钮控制加载→通过→未通过三种状态
  • 加载态：2步流程（照片已拍摄 → 正在核验人脸信息），不暴露后端技术细节
  • 通过态："考勤打卡成功"，不展示核验分数/GPS/核验详情
  • 未通过态：原因说明 + 重新拍摄 + 降级单人打卡选项
  • 严禁暴露：所有文案中不出现"百度API""后端上传""第三方接口"等字眼

3.5 小程序"我的"页面（mp-my.html）

  • 角色切换：手机框外有 demo 切换按钮，实际开发通过登录态自动判定
  • 人员信息：无"打卡人"/"合拍人"角色标签
  • 合拍验证模块：全局可见（两个角色均有），合拍请求不在主页展示卡片

3.6 消息公告页（mp-message.html）

  • 无顶部页签区分，合拍请求混入通知列表
  • 合拍请求消息按钮为"去处理"，跳转 mp-partner-invitation.html

3.7 合拍验证记录（mp-co-photo-records.html）

  • Tab1 抽验记录：我作为打卡人的记录（验证通过/未通过）
  • Tab2 协助记录：我作为合拍人的记录（同意协助/拒绝请求）
  • 无"查看详情"按钮；每条记录字段统一固定

4.2 数据看板（index.html）

包含 5 大区块（从上到下）：

  1. 统计卡片（5个）：启用区县数 / 抽验触发人次 / 抽验通过率 / 预警人次 / 高风险人员数，每卡片右下角有对应子菜单链接
  2. 项目统计表格（左）+ 预警分布（右）：双栏布局。项目表格含风险等级标签；预警分布含4类计数+TOP3高风险人员
  3. 辖区动态表格：账号级别切换控制显示内容（省级→地市 / 市级→区县 / 区县→不显示）
  4. 30天通过率趋势图：SVG折线图，自适应宽度。标注最高/最低点 + 70%参考线

4.3 规则配置（rule-global.html）

双页签（同页面内切换，非跳页）：

  • 全局配置：表格列：组织域/级别/上班卡抽取率/下班卡抽取率/候选人池阈值/人员更换限制/抽验有效期/操作。配置弹窗含：组织域信息（只读）、抽取率、候选人池阈值、下发组织域（树形下拉多选）
  • 项目规则例外：表格列：项目名称|施工许可/项目区划/上级默认规则对比/项目实际规则（橙色🔒标记例外项）/操作。新增例外→模糊搜索选项目；修改例外→项目名只读
关键逻辑：项目规则例外标记 is_locked=true，全局规则下发时跳过这些记录（UPDATE 语句加 WHERE is_locked=false）。

4.4 抽验记录（records.html）

  • 单一表格（去掉页签），列顺序：序号 → 项目名称|施工许可证号 → 项目区划 → 打卡人 → 合拍人 → 类型 → 验证结果 → 未通过原因 → 验证时间 → 操作（详情）
  • 账号级别切换下拉框过滤数据（省级→全部 / 市级→本市 / 区县→本区）

4.5 抽验记录详情（record-detail.html）

  • 双场景支持：默认（拍照重试轨迹）和 ?scenario=swap（换人轨迹）
  • 核验轨迹 Timeline：每次拍照不通过含照片缩略图（点击可查看大图）
  • 三列信息卡片布局（人员/项目/照片），无右侧空白

4.6 抽验汇总（summary.html）

  • 统计周期：上线至今
  • 人员汇总 + 项目汇总 双页签

4.7 风险预警（risk-warning.html）

  • 人员风险 + 项目风险 双页签
  • 统计周期：近30天滚动（页面头部标注）
  • 人员筛选项：风险等级/岗位/项目区划/项目名称
  • 项目筛选项：风险等级/项目区划/项目名称

五、数据流与接口规范

5.1 核心接口时序

步骤触发方方法路径关键参数
单人打卡完成打卡人POST/api/checkin/completeuserId, gps, projectId, checkinType
判定触发抽验后端——按组织域规则+项目例外规则判定
抽取合拍人后端——候选人池查询+随机+分布式锁
推送通知后端WSpush co-photo:notifyrequestId, partnerUserId, expireAt
合拍人确认合拍人POST/api/co-photo/confirmrequestId, action, reason
提交合拍照片打卡人POST/api/co-photo/submitrequestId, image(base64), gps, timestamp
调用人脸核验后端POST/api/co-photo/verify内部调用第三方核验API
返回核验结果后端→打卡人WSpush co-photo:resultresult, score, failReason

5.2 核心数据表

表名核心字段说明
co_photo_requestid, checkin_user_id, partner_user_id, project_id, status(pending/confirmed/rejected/timeout), confirm_at, confirm_deadline, expire_at(15min), result(pass/fail/downgrade), final_score合拍请求主表
co_photo_recordid, request_id, attempt_no, image_url, score, result, fail_reason, gps, camera_device, created_at每次拍照记录（含失败重拍）
co_photo_reject_logid, request_id, user_id, candidate_order, reason, rejected_at拒绝/超时记录
co_photo_ruleid, org_id, org_level, shangban_rate, xiaban_rate, pool_threshold, valid_from, valid_to组织域规则配置
co_photo_rule_exceptionid, project_id, rule_overrides(json), is_locked, created_by, created_at项目规则例外
co_photo_risk_scoreid, target_type(person/project), target_id, score, indicators(json), period_start, period_end, calc_at风险评分（每日凌晨更新）
checkin_record现有表增加字段：co_photo_request_id, is_co_photo_verified, co_photo_result现有考勤表扩展

5.3 定时任务

任务频率逻辑
确认窗口超时扫描每 30 秒扫描 status=pending AND now() > confirm_deadline，自动标记 timeout 并触发换人
执行窗口超时扫描每 30 秒扫描 status=confirmed AND now() > expire_at AND result IS NULL，标记 downgrade
风险评分计算每日 02:00计算近30天数据，生成 person/project 评分
并发控制：抽取合拍人时使用 Redis 分布式锁 (lock:partner:{userId}, TTL=15min)，防止同一人被多个打卡人同时抽中。

八、开发注意事项

严禁向用户暴露任何第三方服务商名称。所有UI文案中不得出现"百度API""百度人脸核验""后端上传""阿里云"等字样。统一使用"人脸核验""系统"等笼统表述。
  1. 打卡人不能拒绝/更换系统分配的合拍人，无对应UI和API
  2. 合拍拍照强制实时拍摄，调用 wx.chooseMedia({ sourceType: ['camera'] })
  3. 照片上传前客户端加水印（GPS+项目+人员+时间）
  4. 规则下发时排除 is_locked=true 的项目例外记录
  5. 风险评分定时任务每日凌晨执行，避免实时计算
  6. 所有时间字段存储为 UTC timestamp，前端展示时按用户时区转换
  7. 侧边栏 7 个菜单图标以 index.html 为基准（统一样式）
  8. 账号级别切换功能在原型中为 demo 下拉框，实际开发通过登录态 org_level 判定
  9. 项目搜索使用 LIKE 模糊匹配（WHERE project_name LIKE '%keyword%'），输入 ≥2 字触发
  10. 折线图/图表类组件建议使用 ECharts，原型的静态 SVG 仅供参考布局
